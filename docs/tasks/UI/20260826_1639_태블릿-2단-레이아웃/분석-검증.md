# 분석 검증

**TL;DR**: 판단 6건과 높이 예산을 세 축으로 검증했다. 구조 근거는 파일·라인으로 모두 확인했고, 요구사항 잠정안 하나를 분석이 뒤집은 것(`Caution` 쪼개기 철회)은 근거가 타당하다. 다만 `ConstraintSet` 이 연결 오버레이의 제약을 보존하는지는 **빌드 전에는 확인할 수 없다.**

## 미검증 — 빌드·실기로만 확인 가능

| 항목 | 왜 지금 못 하나 | 어떻게 확인하나 |
|---|---|---|
| **`ConstraintSet.clone()`→`applyTo()` 가 연결 오버레이(`remote_control_connection_layout`)의 제약을 보존하는가** | 런타임 동작이다 | 태블릿에서 연결 화면이 정상 표시되는지 본다. **계획에 검증 항목으로 넣는다** |
| `applyTo()` 가 가시성을 되돌리지 않는가 | 런타임 동작. `ConstraintSet` 은 가시성도 담는다 | 인플레이트 직후 1회만 적용하므로 이론상 안전. 연결/해제 전환을 눌러 확인 |
| 높이 추정의 오차 | 폰트 실측이 없다 | 실기 캡처 1장 |
| `18dp` 로 키운 뒤 격자 글자가 156dp 를 넘는가 | 렌더링해야 안다 | 태블릿에서 `ellipsize` 발동 여부 확인 |
| 대상 태블릿이 `sw600` 급인지 `sw720` 급인지 | 기기를 모른다 | 앱 로그에 이미 남는다 — `MainActivity.java:340` 이 «가장 작은 변 NNNdp» 를 찍는다 |

> [!TIP]
> **마지막 줄이 유용하다.** 은수님 태블릿에서 앱을 한 번 켜고 로그를 보면 `sw` 값이 바로 나온다. 그러면 두 단으로 나눌 것 없이 그 기기에 맞춰 한 벌로 확정할 수 있다.

## 결론

**분석을 계획으로 넘긴다.** 요구사항 수정 2건(§6)은 계획에 반영한다. 미검증 5건 중 앞의 두 건은 **계획의 검증 항목으로 반드시 올린다.**
