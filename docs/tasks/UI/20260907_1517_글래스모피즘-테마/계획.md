# 계획 — 리모컨 화면 검은 유리

**TL;DR**: 유리를 **밝히지 말고 어둡힌다.** 배경에 색 블롭을 깔고, 컨테이너에는 **검은 반투명 판 + 흰 테두리**를 씌운다. 그러면 화면 전체가 유리가 되면서 **색을 하나도 바꾸지 않아도** 모든 글자가 AA 를 지킨다(최악 지점 5.23:1). 기존 색을 건드리지 않으므로 Java/레이아웃 동기화 문제도 발생하지 않는다.

## 1. 분석 — 왜 이 결론인가

### 1.1 출발점

`ui-glass` 에이전트가 낸 설계([`에이전트-로그/01_ui-glass-설계.md`](에이전트-로그/01_ui-glass-설계.md))를 재계산해 대조했다([`02_오케스트레이터-검산.md`](에이전트-로그/02_오케스트레이터-검산.md)).

파일 근거는 전부 사실이었고, 특히 셋은 이 계획의 뼈대가 됐다.

| 사실 | 근거 | 계획에 미친 영향 |
|---|---|---|
| 이 화면은 이미 어둡다 (`#191919`) | `fragment_remote_control.xml:8` + `colors.xml` (`white_*` 램프가 이름과 반대) | 배경을 어둡게 만드는 일이 아니라 **색을 넣는** 일이다 |
| `setRenderEffect` 는 **자식까지** 흐린다 | Android API 정의 | 배경은 **자식 없는 별도 View** 여야 한다. 루트에 걸면 글자가 다 흐려진다 |
| `realtimeblurview` 를 시도했다 주석 처리한 이력 | `app/build.gradle:74` | 라이브러리 경로는 다시 열지 않는다 |

### 1.2 뒤집은 전제 — 유리는 «밝히는 판»이 아니다

에이전트는 유리 표면을 **흰 오버레이**로만 놓고 풀었다(웹 CSS 의 습관이다). 그 전제에서는 배경이 밝아져 대비가 깎이므로, 경고 빨강 `#FF5252` 때문에 흰빛 상한이 **7%** 로 묶이고 → *"유리라 부르기 민망하니 컨테이너 7개는 불투명으로 지키자"* 는 결론이 나온다.

**어두운 UI 에서 유리는 주변보다 어둡다.** 블롭 배경 위에 검은 판을 얹으면 블롭 색은 비치면서 표면은 어두워져 **대비가 지켜진다.** 에이전트도 `ota_id_box` 에는 «받침(검 40~50%)» 을 처방했으면서 그 원리를 컨테이너에는 적용하지 않았다.

### 1.3 재계산 — 가장 불리한 지점(teal 블롭 중심)에서

| 글자 | 현행 불투명 | **검은 유리 55%** | 검은 유리 45% |
|---|---|---|---|
| ALERT `#FF5252` (병목) | 5.51 | **5.23** AA | 4.85 AA |
| MAP `#F06292` | 5.75 | **5.46** AA | 5.07 AA |
| VOLT `#FFD54F` | 12.46 | **11.83** AA | 10.98 AA |
| TIMING `#4DD0E1` | 9.57 | **9.08** AA | — |
| 본문 `#E5E5E5` | 13.96 | **13.26** AA | 12.30 AA |
| 제조번호 `#66BB6A` | — | **7.06** AA | — |

핑크 블롭 위에서도 55% 기준 ALERT 5.56 · MAP 5.80 으로 통과한다. **잃는 것은 0.3~0.7 포인트뿐이고 전부 AA 안이다.**

### 1.4 테두리는 장식이 아니다

검은 유리는 배경과 밝기 차가 작아(**1.1~1.8:1**) 표면만으로는 카드로 보이지 않는다. 흰 40% 테두리를 얹으면 표면 대비 **3.72~3.81:1** 로 비텍스트 UI 기준 3:1 을 넘긴다.

## 2. 핵심 결정 — 게이트 1

> [!IMPORTANT]
> **게이트 1 통과 — 2026-09-07. 은수님이 네 가지 모두 권장안을 택하셨다.**
> 이에 따라 Step_6(실블러)은 수행하지 않고, 색은 하나도 바꾸지 않는다.

### 결정_1 — 유리를 어느 방식으로 만드는가

- [x] **가. 검은 유리 (권장)** ← **채택** — 컨테이너에 검은 반투명 + 흰 테두리. 화면 전체가 유리가 되고 **색을 하나도 안 바꾼다**
- [ ] 나. 에이전트 원안 — 컨테이너 7개는 불투명 유지, `ota_id_box`·검색 오버레이 2곳만 흰 유리

**권장 근거**: 나안은 화면의 시각 질량 대부분이 불투명으로 남아 «테마를 바꿨다» 고 하기 어렵고, 제조번호가 핑크 블롭 위에서 **3.18:1 로 AA 미달**이다(내 재계산). 가안은 그 미달이 **7.06** 으로 해소된다.

### 결정_2 — 검은 유리의 농도

- [x] **가. 55% (권장)** ← **채택** — 최악 지점 ALERT 5.23:1. 안전 여유가 크다
- [ ] 나. 45% — 최악 지점 ALERT 4.85:1. 블롭 색이 더 비쳐 유리 느낌이 강하다

**권장 근거**: 의료기기라 여유를 택한다. 다만 45% 도 AA 는 지키므로 «유리 느낌이 약하다» 고 보시면 나안이 가능하다. **실기로 보시고 뒤집으셔도 된다** — 값 하나만 바꾸면 되는 구조로 만든다.

### 결정_3 — API 31+ 에서 실블러를 켜는가

- [x] **가. 이번엔 넣지 않는다 (권장)** ← **채택** — 배경이 정적이라 블러 유무의 차이가 블롭 경계의 부드러움뿐이다
- [ ] 나. 넣는다 — 배경 View 에만 `RenderEffect` + 채도 보정

**권장 근거**: 은수님이 «기기 이원화» 를 택하셨으므로 **가안이라도 이원화는 성립한다**(같은 drawable, 블러 한 줄 차이). 먼저 실기로 보시고 «더 흐렸으면» 하실 때 나안을 얹는 편이 되돌리기 쉽다. 나안을 택하셔도 **대비 값은 바뀌지 않는다**(배경 View 만 흐려진다).

### 결정_4 — 블롭에 쓸 색

- [x] **가. 기존 accent `#009688` · error `#EC407A` 재사용 (권장)** ← **채택** — `colors.xml` 에 항목을 안 늘린다
- [ ] 나. 새 색을 들인다

**권장 근거**: 위 대비 계산이 전부 이 두 색 기준이다. 색을 바꾸면 **재계산이 필요하다.**

## 4. 실패 시나리오

**실패_1 — 루트에 블러를 걸어 화면 전체가 흐려진다.**
`setRenderEffect` 는 대상 View 와 **자식 전체**를 흐린다. 배경 drawable 을 루트 `ConstraintLayout` 의 `android:background` 로 걸고 루트에 블러를 걸면 격자 19칸과 버튼 글자가 전부 흐려져 **읽을 수 없는 화면이 배포된다.**
→ 차단: Step_2 에서 배경을 **자식 없는 별도 View** 로 분리한다. 블러는 그 View 에만 건다.

**실패_2 — 테두리를 빼먹어 카드가 사라진다.**
검은 유리는 배경과 밝기 차가 1.1~1.8:1 뿐이다. 테두리를 «장식이니 나중에» 로 미루면 컨테이너 경계가 보이지 않아 **어디까지가 한 묶음인지 구분되지 않는다.** 저시력 사용자에게 특히 그렇다.
→ 차단: Step_3 에서 표면과 테두리를 **한 drawable 안에** 넣어 분리 불가능하게 만든다.

**실패_3 — 블롭이 밝아 대비가 깨진다.**
블롭 알파를 «예쁘니까» 올리면 배경이 밝아지고 검은 유리를 통과한 표면도 밝아진다. 계산은 teal 40% · 핑크 30% 기준이다.
→ 차단: Step_5 에서 **실제 값으로 재계산**한다. 알파를 바꾸면 재계산 없이는 넘어가지 않는다.

**실패_4 — 배경 View 가 터치를 먹는다.**
화면 전체를 덮는 View 를 첫 자식으로 넣으면 z 순서상 아래지만, 크기가 전체라 `clickable` 이 켜지면 뒤 버튼을 가릴 수 있다.
→ 차단: `android:clickable="false"`·`android:focusable="false"` 를 명시하고, 실기에서 모든 버튼을 눌러 본다.
