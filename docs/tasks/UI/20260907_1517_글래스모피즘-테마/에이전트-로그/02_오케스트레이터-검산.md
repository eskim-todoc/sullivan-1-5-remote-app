# ui-glass 설계 검산

**TL;DR**: 파일 근거는 **전부 사실**이고 계산의 뼈대도 맞다. 다만 **블롭 위 합성 수치가 일관되게 실제보다 낙관적**이다(제조번호 3.78 주장 → 실제 3.18). 더 중요한 것은 설계 전제 — 에이전트는 유리를 **«밝히는 판»** 으로만 봤다. **어둡히는 판**으로 뒤집으면 컨테이너 7개 전부를 유리로 만들면서 색을 하나도 안 바꿔도 된다.

## 1. 파일 근거 대조 — 전부 사실

| 에이전트 주장 | 대조 결과 |
|---|---|
| `white_10` = `#FF191919`, 램프 이름이 뒤집힘 | **사실** |
| 격자색 4개가 Java 상수 + 레이아웃 중복 | **사실** (`RemoteControlFragment.java:3381~3384`, 레이아웃 10곳) |
| Java 색 지정은 화면 안에 2곳뿐 | **사실** (앱 전체로는 3곳) |
| `realtimeblurview:1.2.1` 을 시도했다 주석 처리한 이력 | **사실** — `app/build.gradle:74`. 좋은 발견이다 |
| 컨테이너 7개 id 실재 | **사실** (라인은 1씩 어긋나나 무의미) |
| 원형 버튼 전역 `elevation 4dp` | **사실** (`styles.xml:149`) |
| 제조번호 `#66BB6A` | **사실** (`fragment_remote_control.xml:481`) |
| `setRenderEffect` 가 자식까지 흐린다 | **사실** — 배경을 별도 View 로 떼라는 지적은 타당하다 |

## 2. 수치 대조 — 블롭 합성이 낙관적이다

| 항목 | 에이전트 | 재계산 | 차이 |
|---|---|---|---|
| 배지 글자 vs 주황·노랑·초록 | 6.34 / 12.33 / 10.43 | **6.34 / 12.33 / 10.43** | 정확히 일치 |
| 계산 1 표(평면 흰 오버레이) | 12.46 / 9.57 / 5.75 / 5.51 … | 동일 | 일치 |
| 제조번호 vs 흰16%(바탕) | 4.87 | **4.52** | −0.35 |
| 제조번호 vs 흰16%(핑크 블롭) | 3.78 | **3.18** | −0.60 |
| 테두리 흰40% vs 표면 흰16% | ~3.3 | **3.14** | −0.16 |
| ALERT vs teal 블롭(받침 없음) | 2.31 | **1.99** | −0.32 |

**평면 계산은 정확하고 블롭이 낀 계산만 어긋나며, 방향이 한쪽으로 쏠려 있다** — 전부 실제보다 좋게 나왔다. 블롭 중심을 무엇으로 잡았는지가 다른 것으로 보인다. 이 문서는 **재계산 값을 채택**한다.

판정에 뒤집힘은 없다(3.78도 3.18도 미달). 다만 **여유가 에이전트 생각보다 작다.**

## 3. 설계 전제의 문제 — 유리는 «밝히는 판»이 아니다

에이전트의 계산 1·2는 유리 표면을 **흰 오버레이**로만 놓고 풀었다. 웹 CSS 의 습관이다. 그 전제에서는 배경이 밝아지니 대비가 깎이고, 그래서 «7% 상한 → 유리라 부르기 민망 → 컨테이너는 불투명으로 지키자» 는 결론이 나온다.

**어두운 UI 에서 유리는 보통 주변보다 어둡다.** 배경 블롭 위에 **검은 판**을 얹으면 블롭 색은 은은히 비치면서 표면은 어두워져 **대비가 오히려 지켜진다.** 에이전트도 `ota_id_box` 에는 «받침(검 40~50%)» 을 처방했으면서, 그 원리를 컨테이너 7개에는 적용하지 않았다.

### 재계산 — 검은 유리 55% + 블롭 배경

가장 불리한 지점(teal 블롭 중심)에서:

| 글자 | 현행 불투명 `#191919` | **검은 유리 55%** `#07221F` | 증감 |
|---|---|---|---|
| ALERT `#FF5252` | 5.51 | **5.23** AA | −0.28 |
| MAP `#F06292` | 5.75 | **5.46** AA | −0.29 |
| VOLT `#FFD54F` | 12.46 | **11.83** AA | −0.63 |
| TIMING `#4DD0E1` | 9.57 | **9.08** AA | −0.48 |
| 본문 `#E5E5E5` | 13.96 | **13.26** AA | −0.70 |
| 제조번호 `#66BB6A` | — | **7.06** AA | 에이전트안(3.18 미달)을 **해소** |

핑크 블롭 위에서도 ALERT 5.56 · MAP 5.80 으로 통과한다.

**잃는 것은 0.3~0.7 포인트뿐이고 전부 AA 안에 있다.** 그리고 색을 **하나도 바꾸지 않는다** — 에이전트가 갈래_나를 각하한 이유(경고색을 흐리게 만들 수 없다)를 그대로 지키면서 유리를 얻는다.

### 경계 시인성

검은 유리는 배경과의 밝기 차가 작아(1.1~1.8:1) **표면만으로는 카드로 안 보인다.** 흰 40% 테두리를 얹으면 표면 대비 **3.72~3.81:1** 로 비텍스트 UI 기준 3:1 을 넘긴다. **테두리는 장식이 아니라 필수 부품이다.**

## 4. 채택·기각

| 항목 | 판정 |
|---|---|
| 배경 View 를 자식 없는 별도 View 로 분리 | **채택** — `setRenderEffect` 가 자식까지 흐리므로 옳다 |
| 블롭 배경(accent·error 재사용, 새 색 안 늘림) | **채택** |
| 라이브러리 추가 없이 간다 | **채택** — `realtimeblurview` 주석 이력이 근거를 보탠다 |
| 이 화면의 로컬 관례(둥근 4dp)를 따르고 전역 cut 을 강제 안 함 | **채택** |
| 위험_1~6 | **채택** (위험_1 은 검은 유리 채택으로 해소) |
| **컨테이너 7개를 불투명으로 남긴다** | **기각** — §3. 검은 유리로 승격해도 AA 를 지킨다. 화면의 시각 질량 대부분을 불투명으로 두면 은수님이 지시하신 «테마 변경» 이 성립하지 않는다 |
| 흰 16% 유리(`ota_id_box`·검색 오버레이) | **기각** — 같은 이유로 검은 유리로 통일한다. 제조번호 미달도 함께 사라진다 |

## 5. 남는 판단은 게이트 1 로

검은 유리의 농도(45% / 55%)는 «유리 느낌 ↔ 대비 여유» 의 맞바꿈이라 은수님이 정하실 일이다. `계획.md` §핵심 결정으로 올린다.
