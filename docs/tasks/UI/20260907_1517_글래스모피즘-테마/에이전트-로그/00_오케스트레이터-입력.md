# 오케스트레이터 입력

**TL;DR**: 은수님이 `ui-glass` 활용을 **명시 지정**하셨다. 게이트 1 전이므로 **읽기 전용 1노드**만 띄웠고, 산출물은 로그 파일 쓰기로 한정했다. 위임의 초점은 «예쁜 유리»가 아니라 **`minSdk 23` 에서 성립하는가**와 **의료기기 가독성을 깎지 않는가** 둘이다.

## 은수님 입력 (원문)

> ui-glass 에이전트와 함께 지금 앱 디자인을 글래스모피즘 테마로 변경해봐.

## 위임 설계

| 항목 | 결정 | 근거 |
|---|---|---|
| 위임 여부 | **위임** | 은수님이 에이전트를 지목하셨다 — 트리거 충족 |
| 노드 수 | **1** (`ui-glass`) | 지목된 하나뿐. 색·안전 심사는 결과가 나온 뒤 필요하면 추가 |
| 모델 | `sonnet` | 헌법 §5 — 세션이 Opus 여도 서브에이전트는 Sonnet 고정 |
| effort | 미지정 | 헌법 §5 — 세션 상속 |
| 쓰기 권한 | **로그 파일만** | 헌법 §3 — 게이트 1 전은 read-only fan-out |

## 위임 프롬프트에 실어 보낸 경계

1. **소스 수정 금지**, 결과는 지정 로그 파일에 직접 Write
2. **`minSdk 23`** 을 움직일 수 없는 제약으로 못박음 — API 31+ 실블러와 23~30 폴백을 갈라서 설계할 것
3. **의료기기**임을 명시 — 상태값·경고 텍스트 WCAG AA 이상, 최악 배경 양단에서 대비비를 **계산**해서 제시. "충분해 보인다" 금지
4. XML View 시스템(Compose 아님), `cornerFamily: cut`, 나눔고딕 등 현행 어휘 전달
5. **전면 적용안은 반대 근거와 함께 각하**하고 등급을 나눌 것 — 18개 화면 전부에 유리를 씌우는 결론을 막기 위한 장치
6. 문서 규약(frontmatter·TL;DR·Mermaid·한글 라벨·`파일:라인` 근거·`(미확인)` 표기)

## 검증 계획

에이전트 결과는 **그대로 신뢰하지 않는다.** 받은 뒤 오케스트레이터가 직접 확인할 것:

| 축 | 방법 |
|---|---|
| 대비비 수치 | 제시된 색 조합을 **재계산**해 대조 |
| API 경계 주장 | `RenderEffect` 등 API 도입 레벨을 문서로 확인 |
| `파일:라인` 근거 | 실제 파일에서 대조 (앞서 본 세션에서 라인 오기 사례 있음) |
| 범위 등급 | 화면 18개에 실제로 대응되는지 |
