## 목표와 범위

사용자는 현재 상태 커밋과 이름 뒤 multi가 붙은 새 브랜치를 요청한 뒤 다중 연결을 추가하고 싶다고 했다. 기존 연결을 유지하면서 여러 외부기에 동시에 BLE 연결하고 한 번에 명확히 선택한 장치 하나를 제어한다. 현재 상태·글래스·서체·하단 탭 구조를 유지하고 앱바 아래에 작은 제어 대상 선택행과 전체 연결 목록을 추가한다. 방송식 일괄 명령은 이번 범위가 아니다.

현재 브랜치는 develop_ota_landscape_multi, 기준은5e259bb다. 제품 구현18be231과 시안/시험 기록5e259bb를 기존 develop_ota_landscape에 남겼다. 푸시는 요청되지 않아 수행하지 않았다. 서명 설정 source/gradle.properties와 source/.idea/deploymentTargetSelector.xml의 기존 로컬 변경은 보존하고 커밋에서 제외했다. 새 다중 연결 구현은 이번 커밋 요청 범위와 구분한다.

현재 확인 가능한 실기는 R3CM7068Y6P/SM-G977N과 FFFF/내부기#196FFFFF의 미착용 시험 보드다. 두 번째 실물 외부기 준비 가능 여부는 사용자에게 비동기 질문했다. 답이 없어도 구현과 가짜 두 장치의 격리 검증은 계속하며, 실제 두 GATT 동시 연결 성공은 장비 없이 통과로 기록하지 않는다.

## 수용 기준

1. 주소와 연결 세대별로 GATT·특성·인증 대상·기능 지원·상태·조회/쓰기 큐·FF·OTA·관리 결과를 소유한다. 같은 FFFF 제조번호도 다른 주소면 구분한다.
2. A의 연결 종료·오래된 콜백·재시도·대기 작업이 B의 상태·명령·타이머를 바꾸지 않는다. 버튼 입력 당시 대상이 큐 처리 중 바뀌지 않는다.
3. 추가 검색과 연결이 기존 연결을 끊지 않는다. 사용자 선택 없이 주변 장치 전체에 자동 연결하지 않는다.
4. 선택 변경은 기본 사용자 DB 값을 바꾸지 않는다. 신원·측정값·지원 기능이 같은 세션에 속하고 관리 결과와 로그의 출처가 구분된다.
5. FF/관리/파일 수집 중 대상 변경과 전송 중 해당 장치의 해제를 막는다. OTA는 장치 세션이 소유하여 다른 장치를 선택해도 계속한다. 기존 단일 장치 기본/특수/FF/OTA 동작과49개 시험을 보존한다.
6. 사용자·외부기 등록 정보가 어느 연결에서든 사용 중이면 편집/삭제 보호를 적용한다. 기존 등록 DB의 마이그레이션은 요구하지 않는다.
7. 가짜2세션 시험과 실제1대/2대 시험을 구분하고, 빌드·설치·화면/제어 결과와 미실행 범위를 기록한다.

## 근거와 실행 계획

시작 당시 MainActivity의 서비스 발견·CCCD 인증·characteristicChanged와 disconnect가 전역 상태를 참조했다. Status와 Ota의 싱글턴, static Ota.fileList, Activity 단일 ViewModel과 전역 관리 결과가 장치 상태를 공유했다. 단일 mBluetoothGatt만 Map으로 바꾸는 접근을 배제하고, 지연 Runnable에서 전역 필드를 일시적으로 교체하는 방식도 쓰지 않았다.

장치별 엔진이 자기 콜백·큐·타이머를 소유하고 Activity는 권한·스캔·장치 선택과 기존 UI API의 전달을 맡는다. Activity의 선택 상태 별칭은 UI 읽기와 즉시 명령 전달에만 사용한다. 내부 프로토콜 흐름은 선택 포인터를 다시 읽지 않는다. 화면에서 보이지 않는 장치도 자기 상태를 갱신한다. 장치 종료 시 다른 제어 대상으로 자동 전환하지 않는다.

| 소유자 | 변경 범위 | 반환 근거 |
|---|---|---|
| native_remote | MainActivity, connection/session 패키지, Status/Ota/StatusViewModel, 백엔드 시험 | 세션 격리 구조와 API, 변경 파일, 호스트 시험 경계 |
| multi_connection_ui | RemoteControlFragment/XML, 연결 목록 Dialog, 관리/CRUD 보호 | 선택 세션 observer 수명, 대상 표시·연결/해제 흐름 |
| 루트 | 작업 기록, 통합·빌드·설치·실기·독립 검토 수렴 | 실제 검증 결과와 기능 한계 |

공유 계약은 connection.ConnectionInfo와 Activity의 getSelectedStatusViewModel/getSelectedSessionId/getConnectionStates/getSelectedManagementResult/getAdditionalScanState 및 추가 검색·연결·선택·개별 종료·모든 세션 in-use 검사 API다. DTO는 주소·라벨·연결 상태·선택·등록 여부를 가진다. 기존 public 제어 API를 유지한다. 에이전트끼리 같은 파일을 수정하지 않는다.

### 후속 OTA 요구와 구현 계약

사용자는 PC 리모콘처럼 **OTA 준비**에서 `0x60`으로 매핑 모드에 들어간 뒤 전송하고, 내부기 연결이 없어져도 BLE를 유지하며, **네 파일의 합산 바이트**로 전체 진행률을 표시하라고 추가 요청했다. OTA 화면에서 전체 장치와 각 장치의 진행률을 함께 보는 것이 목표다.

현재 PC 소스 `python-remote-app/new-remote-app/src/tdc_remote/feature/tdc_remote_ctrl.py:84`, `protocol/tdc_packet_parse.py:121`, `ui/tdc_multi_ota_panel.py:1537`을 대조했다. 준비 요청은 선택한 한 장치에 보내는 1바이트 `60`이며, 정확한 2바이트 `60 01` 응답만 성공이다. `60 00`, 잘못된 길이, 오류 응답, 시간 초과는 실패로 처리한다. `61`은 준비 취소로 쓰지 않는다.

- 장치별 준비 상태와 순차 전송을 DeviceSession/OtaCoordinator가 소유한다. Fragment는 파일 수집과 화면 표시·사용자 명령 전달을 맡는다.
- 준비 응답 전에는 전송을 시작하지 않는다. 각 장치를 따로 준비하고 시작하며, 장치 선택이 바뀌어도 원래 세션의 전송은 계속한다.
- 분모는 시작 당시 네 파일의 합산 크기로 고정한다. 분자는 해당 장치에서 ACK를 받은 바이트의 합이다. 파일별 퍼센트의 단순 평균을 쓰지 않으며 마지막 ACK 전에는 100%로 표시하지 않는다.
- 목록에는 장치 식별, 선택 여부, 준비 전/준비 중/준비됨/전송 중/완료/실패, 전체 %, 바이트와 현재 파일을 표시한다.
- 매핑 상태에서는 내부기 의존 일반 조회를 쉬고 BLE를 유지한다. 슬롯 부팅/공장 FF 복귀가 GATT를 끊지 않을 수도 있으므로 해당 세션의 매핑 상태 해제와 일반 조회 재개를 명시적으로 처리한다.

1차 통합 설치본의 OTA 결과는 후속 OtaCoordinator 설치본의 실기 통과로 재사용하지 않는다. 최종 APK·시험 수와 실제 재시험 결과를 별도로 남긴다.

후속 엔진 구현의 첫 통합 빌드와 총 78개 호스트 시험은 통과했다(기존 67개 + OtaCoordinatorTest 11개). 독립 검토에서 단계가 다른 늦은 ACK가 현재 타임아웃을 지울 수 있는 문제를 찾아 단계 일치 검사와 회귀시험으로 수정했다. 추가로 일반 조회가 BUSY일 때 게시된 가용성 값이 IDLE 전환 후 갱신되지 않을 수 있어, 표시 시 현재 세션의 준비/시작 가능 여부를 다시 평가하는 API로 보완 중이다. 이 설치본의 최종 실기 결과는 아직 대기다.

## 현재 사용 순서

1. 제어 대상에서 연결할 장치를 선택한다. 추가 검색·연결은 기존 장치 연결을 유지한다.
2. OTA에서 해당 장치의 **OTA 준비**를 누른다. `60 01` 확인 후 준비됨으로 바뀐다. 준비만으로 파일 전송을 시작하지 않는다.
3. 파일 폴더에서 MFST·APP0·APP1·APP2 네 파일의 수집이 모두 끝났는지 확인한다.
4. 업데이트할 슬롯 1 또는 2를 선택한 뒤 **업데이트 시작**을 누른다.
5. **장치별 OTA 진행**의 전체 %는 그 장치가 ACK한 바이트 ÷ 시작 시 고정된 네 파일 합계다. 최종 데이터 ACK 전까지 100%로 올리지 않는다.
6. 다른 장치를 선택하여 그 장치도 준비·파일·슬롯·시작을 따로 실행할 수 있다. 먼저 시작한 전송은 계속되며 목록에서 각 진행률을 본다. 이 병행 흐름은 가짜 두 전송 엔진에서 확인했고 실제 두 외부기 무선 시험은 남아 있다.

현재 보드는 전원/부팅 확인이 필요하므로 실제 사용 재개 전 전원 재인가 및 남은 부팅·제어 시험을 수행한다. 전체 시험과 사용법의 최신 열람본은 [전체 시험 목록](E:/workspace/html/제품/TD2-Remote-Application/앱-검증/전체-시험-목록/index.html)이다. 다중 연결 이후 소스는 아직 커밋하지 않았다.

공식 지침의 공통 근거는 글꼴을 여러 개 섞는 것보다 역할별 굵기·색·기준선과 숫자 정렬을 체계화한다는 것이다. Material3는 display/headline/title/body/label 역할과 값이 자주 바뀌는 곳의 고정폭 숫자를 설명한다. Carbon은 입력·제어가 많은 생산적 UI에서 공간 효율과 compact 본문/제목의 행높이 짝을 강조한다. Adobe Spectrum은 정보 계층을 크기·굵기·색으로 표현하고 역할별 스타일을 유지한다. 세 문서 사례를 전체 시장의 점유율이나 모든 앱의 유행 통계로 확대하지 않는다.

- [Material3 Applying type](https://m3.material.io/styles/typography/applying-type)
- [Carbon Typography style strategies](https://www.carbondesignsystem.com/building-blocks/foundations/typography/style-strategies)
- [Adobe Spectrum Typography system](https://spectrum.adobe.com/foundations/typography/typography-system)

현재 권장안은 SUIT 한 가족으로 한글·영문을 통일하고 항목500/값700, 같은12sp 크기와 일정한 값 열을 쓰는 것이다. 실제 조합 시안에서는13px(현재12sp와 폰 글자 배율1.1 근사)·값600/700 전환으로 비교한다. 대안은 영문/숫자 Inter + 한글 SUIT, 또는 Wanted Sans다. 이는 UI 적합성을 근거로 한 판단이며 인기 순위 주장이 아니다.

SUIT 공식 설명은 UI용 제작, 한글과 조화시킨 영문·숫자, 고정폭 숫자(tnum), 시리얼 식별용 글자(ss17)를 제시한다. Inter는 작은 text optical design과 높은 소문자 높이, 고정폭 숫자 및 슬래시0을 지원한다. Wanted Sans는 한글·로마자와7기본 굵기를 제공한다. 새 원본 세 파일 모두 실제wght700/tnum이 있으나 ㎃/㎽/Ｖ/㎷ 글리프는 없어, 비교 시안에서는 단위만 기존Plex KR로 보완했다. 앱 적용 시에도 이 범위를 고려해야 한다. 이 조사에는 앱 재빌드·전체 시험을 추가하지 않았다.
