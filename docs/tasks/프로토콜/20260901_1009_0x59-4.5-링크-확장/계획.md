# 계획

**TL;DR**: 5개 파일에 **7단계**로 넣는다. 상수 → 뷰모델 → 읽기 → 쓰기 → 다이얼로그 → 하한 보호 → 화면. **기존 인덱스의 동작은 한 줄도 바꾸지 않는다.** 열어 둔 결정 3건은 분석의 기울기대로 확정한다.

## 0. 확정한 결정

| 결정 | 확정 | 근거 |
|---|---|---|
| 앱 Default 상수(160·200) 갱신 | **하지 않는다.** 보고만 | 지시 범위 밖이고 링크 동작에 직접 영향. 은수님 판단 사항 |
| 하한 > 상한 차단 | **목록에서 제외** | 거부될 값을 고르게 하지 않는다(요구사항_3 과 일관) |
| 버튼 이름 | **`Max PMIC`** | 3형제가 `Normal`·`BT`·`Fixed` 로 영문 축약 |

## 1. 단계

### 단계 1 — 상수 (`params/PacketInfo.java`)

```java
// 인덱스
static public final int RC_LINK_IDX_MAX_TX_POWER = 16; // 링크 Tx 파워 상한 (4.5+, 전체 읽기에 안 실림)
static public final int RC_LINK_IDX_MAX = 16;          // 15 → 16

// 버전
static public final int RC_PROTOCOL_MINOR_MAX_TX_POWER = 5;

// 선택 범위
static public final int MAX_TX_PWR_SELECT_MAX = 214; // HW 상한. 하한선은 인덱스 3·4 로 계산한다
static public final int MAX_TX_PWR_DEFAULT    = 214; // 5.350V — 펌웨어 MaxVoltageControlValue
```

> `MAX_TX_PWR_SELECT_MIN` 은 **두지 않는다.** 상수가 아니라 계산값(`max(idx3, idx4) + 1`)이기 때문이다.
> 상수로 두면 그 순간 낡는다 — 요구사항_4b 가 정확히 그렇게 낡은 사례다.

**하한선 계산을 `PacketInfo` 에 함수로 둔다.** 다이얼로그 두 곳(상한 선택·하한 검사)이 같은 식을 써야 한다.

```java
/** 상한이 넘어야 하는 바닥. 펌웨어 tdc_get_max_tx_power_level_floor() 와 같은 식이다. */
static public int makeMaxTxPowerFloor(int minLevel, int mappingLevel) { ... }
```

### 단계 2 — 뷰모델 (`view_model/StatusViewModel.java`)

`MinTxPowerLevel` 한 벌을 그대로 본떠 `MaxTxPowerLevel` 을 만든다 — LiveData · getter · setter. 초기값은 `LINK_VALUE_UNKNOWN`.

### 단계 3 — 읽기 (`activity/MainActivity.java`)

| 무엇 | 어디 |
|---|---|
| `isLinkParamSupported` 에 `case RC_LINK_IDX_MAX_TX_POWER:` → `isProtocolAtLeast(4, 5)` | `:952` 의 `switch` |
| `isMaxTxPowerSupported()` 신설 (기능 게이트, `isCoinCountSupported()` 와 같은 형태) | `:1175` 근처 |
| `applyLinkParam` 에 `case RC_LINK_IDX_MAX_TX_POWER:` → 뷰모델 반영 | `:2597` 의 `switch` |
| **① 판별 완료 시점의 자동 읽기** | `advanceProbe()` 의 `PROBE_STEP_GATING` 분기, `mProbeStep = PROBE_STEP_NONE` 직후(`:1546`) |
| **② 갱신 때의 재읽기** | `handleRcLinkResponse()` 의 `RC_IDX_ALL` 분기 끝(`:2576` `notifyLinkParamsRefreshed()` 직전) |
| 자동 읽기 응답의 토스트 억제 | `:2589` 의 개별 응답 토스트 조건 |
| 연결 해제 시 `LINK_VALUE_UNKNOWN` 으로 초기화 | `:2952` 근처의 기존 초기화 블록 |

> [!IMPORTANT]
> **은수님 지시 (2026-09-01)** — *"4.5는 인덱스가 별도이니 4.5로 판단되는 시점에 상한 PMIC도
> 추가로 한번 읽어서 상태 정보를 표시하게 자동으로 해야해."*
>
> **«4.5로 판단되는 시점» 은 판별 시퀀스가 끝나는 자리다.** 순서가
> `PROBE_STEP_VERSION`(버전 확정) → `PROBE_STEP_LINK_ALL` → `PROBE_STEP_GATING` → `NONE` 이므로
> (`MainActivity.java:1505~1550`), 마지막 자리에서는 **버전이 이미 확정**되어 있고
> **판별 상태 기계가 끝나 패킷이 겹치지 않는다.**
>
> 전체 읽기 응답 자리(②)만 쓰지 않는 이유 — 그 시점은 판별 **중**이라
> 뒤이어 게이팅 요청이 나가면서 응답 두 개가 동시에 뜬다. 옵션 번호가 달라 오작동은 안 하지만,
> «판별이 끝난 뒤 한 번» 이라는 지시에 정확히 맞추려면 ① 이 맞다.
>
> **중복 방지** — ② 는 `isLinkInfoReadIdle()` 이 참일 때만 보낸다. 즉 연결 직후에는 ① 만,
> 그 뒤 갱신에서는 ② 만 나간다.
>
> **토스트 억제** — 개별 읽기 응답은 `isLinkInfoReadIdle()` 이면 토스트를 띄운다(`:2589`).
> 자동 읽기는 사용자가 누른 것이 아니므로 그 한 번을 억제한다. 안 하면 **연결할 때마다 토스트가 뜬다.**

### 단계 4 — 쓰기 (`activity/MainActivity.java`)

```java
public void sendMaxTxPower(int level)   // 인덱스 16 쓰기 + 쓰기 뒤 개별 읽기로 확인
```

**에러 문맥.** `mStatus.pendingMaxTxPowerWrite` 플래그를 두고 쓰기 시 켠다. 3.5초 뒤 자동 해제(선례: `isEnabledInvalidPacketToast` 의 억제 타이머). 에러 `case 2` 에서 이 플래그가 켜져 있으면 **«범위 밖» 전용 문구**를 띄운다.

```
"PMIC 상한은 NNN 이상이어야 합니다 (하한 설정 때문). 지금 범위: NNN ~ 214"
```

그 외(플래그 꺼짐 또는 다른 에러 타입)는 **기존 문구 그대로** — 기존 동작을 바꾸지 않는다.

### 단계 5 — 상한 다이얼로그 (`fragment/RemoteControlFragment.java`)

`makeDialog_maxTxPowerSelect()` 를 3형제 형태로 만든다. 다른 점만 적는다.

- 목록 시작점 = `makeMaxTxPowerFloor(읽은 idx3, 읽은 idx4) + 1`, 끝 = 214
- 하한 둘 중 **어느 쪽이 바닥을 밀어 올렸는지** 를 다이얼로그 메시지에 적는다
- 현재 값보다 **낮은 값을 고르면** 「지금 파워는 바로 내려가지 않습니다」 안내
- `Default` 는 214

### 단계 6 — 하한 다이얼로그 보호 (`fragment/RemoteControlFragment.java`)

`makeDialog_minTxPowerSelect()`·`makeDialog_mappingTxPowerSelect()` 두 곳의 목록 끝을 바꾼다.

```
maxLevel = min(MIN_TX_PWR_SELECT_MAX, 읽은 상한 - 1)     // 상한을 못 읽었으면 기존 값 그대로
```

**상한이 `LINK_VALUE_UNKNOWN` 이거나 4.5 미만이면 손대지 않는다** — 퇴행 방지(분석 §2.2).

### 단계 7 — 화면 (`res/layout/fragment_remote_control.xml` + 프래그먼트)

- Etc 2행의 `Space` 를 `Max PMIC` 버튼으로 교체 (4열 격자 유지)
- 상태 표시 1행에 상한 값 추가 — `Cur` / `PMIC` / `Map` / `Fix` 옆
- 4.5 미만이면 버튼·표시 **숨김**

## 2. 손대지 않는 것

| 무엇 | 왜 |
|---|---|
| 전체 읽기 파서의 `Math.min` | 4.5 응답도 값 15개다. 그대로 안전하다 |
| 인덱스 6(강제 고정)의 214 | 정책 상한에 묶이지 않는다 |
| 에러 `case 1`·`case 8` 과 문맥 밖 `case 2` | 기존 문구 유지 |
| 앱 Default 상수 160·200 | §0 |

## 3. 검증 계획 (단계 ⑧에서 수행)

| 축 | 어떻게 |
|---|---|
| 빌드 | `gradlew assembleDebug` 통과 |
| 4.3·4.4 퇴행 | 게이트가 `case` 로 갈리는지 코드로 확인. 인덱스 16 송신 경로가 `isMaxTxPowerSupported()` 뒤에만 있는지 `grep` 전수 |
| 하한선 계산 | `makeMaxTxPowerFloor` 가 펌웨어 `tdc_get_max_tx_power_level_floor()` 와 같은 식인지 대조 |
| 실기 | **불가.** `docs/상시 점검 대장.md` 에 항목을 쌓는다 |

## 4. 실기 확인 항목 (쌓아 둘 것)

1. 4.5 기기에서 인덱스 16 개별 읽기가 값을 돌려주는가
2. 하한선 미만을 쓰면 에러 타입 2 가 오는가, 앱 문구가 «범위 밖» 으로 갈리는가
3. 상한을 낮춘 뒤 인덱스 1 이 즉시 안 내려가는가 (정상 동작 확인)
4. 4.3·4.4 기기에서 `Max PMIC` 가 숨겨지고 기존 동작이 그대로인가
5. 리셋 직후 첫 연결에서 214 가 쓰이는가 (`TDC_LINK_MAX_POWER_SAFE_BOOT`)
