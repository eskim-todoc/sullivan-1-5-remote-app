# 구현 검증 — 피드포워드 (인덱스 17~26)

**TL;DR**: 5개 파일에 반영, **`assembleDebug` 통과**. 계획의 검증 축 셋을 실제로 돌려 전부 통과했다. **핵심은 읽기 큐**다 — 그것 없이는 연결 직후 읽을 8개 중 7개가 조용히 사라진다.

## 1. 지침 준수

| 항목 | 판정 |
|---|---|
| 단계 ⑦ 진입 승인 | 통과 — 2026-09-01 *"기존 4.5를 하위호환하는건 없어도 되는거 알지? … 계속 연장선에 있는거야"* 를 진행 지시로 받았다 |
| 작업 폴더 | **하나로 합쳤다** — 은수님이 «4.5 는 끝난 게 아니라 연장선» 이라 하셨다. `20260901_1009_0x59-4.5-링크-확장` 아래 인덱스 16 문서와 피드포워드 문서가 같이 있다 |
| 기존 관례 | 통과 — 다이얼로그·게이팅·경고 모두 기존 형태를 본떴다 |
| AI 표시 금지 | 통과 |

## 2. 철회한 요구사항

**요구사항_5 «없는 인덱스의 거절을 조용히 흘린다» 를 철회했다.**

그 요구는 «인덱스 16 만 있는 4.5»(커밋 `607ab9e`)를 배려하려던 것인데, 은수님이 **그럴 필요 없다**고 하셨다. 4.5 는 «16 + 17~26» 하나뿐이고 중간 상태는 없는 것으로 본다.

**대신 견고성 하나만 남겼다** — 읽기 큐는 거절이 와도 다음 인덱스로 넘어간다(`MainActivity.java` 에러 분기의 `pumpLinkReadQueue()`). 하나에 막히면 뒤가 영영 안 읽힌다. 토스트 동작은 기존 그대로다.

> **4.3·4.4 하위 호환은 별개이고 그대로 지킨다.** 철회한 것은 «4.5 안에서의 중간 상태» 배려뿐이다.

## 3. 구현 결과

### 3.1 읽기 큐 — 이 작업의 중심

```java
private final ArrayDeque<Integer> mLinkReadQueue = new ArrayDeque<>();
private void enqueueLinkRead(int... indexes)   // 넣고 하나 보낸다
private void pumpLinkReadQueue()               // 응답·거절 자리에서 다음 하나
```

`sendPacket()` 이 `transferState == BUSY` 면 패킷을 **조용히 버리기** 때문에 필요하다. 연결 직후 읽을 것이 **8개**(16 + 17~23)라, 큐가 없으면 7개가 사라진다.

| 안전장치 | 내용 |
|---|---|
| 중복 방지 | 이미 큐에 있는 인덱스는 다시 넣지 않는다 |
| 시한 | 3.5초 안에 응답이 없으면 큐를 비운다. 못 읽은 값은 «모름» 으로 남아 화면에 `-` 로 보인다 |
| 거절 내성 | 에러 분기에서도 `pumpLinkReadQueue()` 를 부른다 |
| 연결 해제 | 큐를 비운다 |

**인덱스 16 도 이 큐로 옮겨** 개별 읽기 경로를 하나로 만들었다.

## 5. 실기 확인 대기 항목

1. 연결 후 **17~23 이 하나도 빠짐없이** 읽히는가 (큐가 도는가) — 로그 `[LINK] 큐에서 인덱스 N 를 읽습니다` 8줄
2. FF 를 켜고 제어 모드 1 로 두면 경고가 뜨는가
3. 스텝 4 · 쿨다운 50 이면 «초당 상승 80스텝» 경고가 뜨는가
4. FF 다이얼로그를 열 때 24·25·26 이 갱신되는가
5. 4.3·4.4 에서 `FF` 버튼이 숨겨지고 기존 동작이 그대로인가
6. 세움−올림 차분이 랩(255→0)을 넘어도 맞게 보이는가

## 6. 사고 기록

**셸 heredoc 이 또 문제를 일으켰다.** Java 블록을 파이썬 heredoc 으로 넣으려다 인용이 깨졌다
(`unexpected EOF while looking for matching`). 앞서 같은 세션에서 `\n` 이 실제 줄바꿈이 된 사고도 있었다.

> **결론 — Java 코드 블록은 셸을 거치지 않는 편집 도구로 넣는다.** 이 저장소에서 네 번째다.
