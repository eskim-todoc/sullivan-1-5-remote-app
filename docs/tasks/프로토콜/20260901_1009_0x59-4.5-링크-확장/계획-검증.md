# 계획 검증

**TL;DR**: 7단계가 요구사항 8건을 **빠짐없이 덮는다.** 하위 호환 퇴행 경로를 전수로 짚었고, 계획이 스스로 만드는 새 위험 2건을 찾아 완화를 붙였다. **단계 ⑦ 진입 가능** — 다만 은수님 승인이 필요하다.

## 1. 지침 준수

| 항목 | 판정 |
|---|---|
| 산출물 ⑤ 위치·이름 | 통과 |
| 단계 ⑦ 진입 전 사용자 승인 | **대기 중** — 이 문서가 마지막 자체 검증이다 |
| `tdc_` 접두어 (신규 심볼) | **해당 없음** — 이 저장소는 안드로이드 앱이고 기존 심볼이 `sendXxx`·`makeDialog_xxx` 관례다. 새 심볼도 그 관례를 따른다 |
| 기존 파일 리팩토링 금지 아님 | 통과 — 기존 함수 형태를 본뜨기만 한다 |
| 브랜치 | **확인 필요** — 현재 `develop_ota`. 4.4 작업도 같은 브랜치에서 진행됐다(`ee94c86`). 관례를 따른다 |

## 2. 논리적 정합성

### 2.1 요구사항 → 계획 단계 대응

| 요구사항 | 계획 단계 | 덮였나 |
|---|---|---|
| 1 버전 게이팅 | 3 (`case 16` + `isMaxTxPowerSupported`) · 7 (숨김) | ✔ |
| 2 개별 읽기 | 3 (전체 읽기 응답 자리에 부착) | ✔ |
| 3 하한선 계산 | 1 (`makeMaxTxPowerFloor`) · 5 (목록 시작점) | ✔ |
| 4 하한 > 상한 차단 | 6 | ✔ |
| 4b Default 상수 보고 | §0 (보고만) | ✔ |
| 5 거부 사유 구분 | 4 (문맥 플래그 + `case 2` 분기) | ✔ |
| 6 «지금 파워는 그대로» | 5 (낮출 때 안내) | ✔ |
| 7 화면 표시 | 7 | ✔ |

**누락 없음.**

### 2.2 하위 호환 퇴행 경로 전수

«4.3·4.4 기기에서 동작이 바뀌는 길» 을 모두 세었다.

| 경로 | 바뀌나 | 왜 |
|---|---|---|
| `RC_LINK_IDX_MAX` 15 → 16 | **안 바뀜** | 전체 읽기 파서는 `min(valueLen=15, 16)` = 15 |
| 게이트 `default` | **안 바뀜** | `case 16` 을 명시해 `default` 로 안 떨어진다 |
| 인덱스 16 개별 읽기 송신 | **안 나감** | `isMaxTxPowerSupported()` 뒤 |
| 하한 다이얼로그 목록 끝 | **안 바뀜** | 상한이 `UNKNOWN` 이거나 4.5 미만이면 기존 `MIN_TX_PWR_SELECT_MAX` 그대로 |
| 에러 문구 | **안 바뀜** | 문맥 플래그가 꺼져 있으면 기존 분기 |
| 화면 | **안 바뀜** | 4.5 미만이면 버튼·표시 숨김 |

**여섯 경로 모두 «4.5 에서만 켜진다».**

### 2.3 계획이 새로 만드는 위험

| # | 위험 | 완화 | 계획 반영 |
|---|---|---|---|
| A | **전체 읽기 응답 자리에서 개별 읽기를 또 보내면 재귀가 되나** | 인덱스 16 응답은 `RC_IDX_ALL` 분기로 안 들어가고 개별 분기로 간다. **재귀 없음** | 단계 3 |
| B | **하한 다이얼로그의 목록 끝이 «상한 − 1» 로 좁아져 기존 값이 목록 밖이 될 수 있다** | 현재 값이 목록 밖이면 체크 위치 계산이 깨진다(기존 코드가 `currentLevel - minLevel` 로 인덱스를 만든다). **범위 밖이면 기본값 위치를 가리키는 기존 방어**(`RemoteControlFragment.java:1456~1459`)가 이미 있으나, **그 기본값(160·200)조차 목록 밖일 수 있다** | **계획 보강 필요** ↓ |

> [!WARNING]
> **위험 B 는 계획에 빠져 있었다. 단계 6 에 한 줄을 더한다.**
>
> 목록 끝을 좁힐 때 **체크 인덱스를 목록 범위로 클램프**한다. 클램프해도 벗어나면 «선택 없음»(-1)으로 둔다.
> `setSingleChoiceItems` 는 -1 을 «아무것도 안 골림» 으로 받으므로 안전하다.
>
> 이 검사를 빼면 **상한을 180 으로 낮춘 뒤 매핑 하한 다이얼로그를 여는 순간 인덱스가 음수/범위 밖**이 된다.

### 2.4 «쓰기 뒤 개별 읽기» 가 과한가

과하지 않다. 분석 §4 «남은 불확실 2»(쓰기 성공 응답이 값을 되돌려 주는지 미확인)를 **어느 쪽이든 안전하게** 만드는 값싼 수단이다. 선례도 있다 — 4.4 코인 작업이 쓰기 뒤 `requestLinkParamRefresh("코인 설정")` 을 부른다(`MainActivity.java:2371`).

## 4. 판정

**단계 ⑤ 통과 — 단, §2.3 위험 B 의 보강을 단계 6 에 반영한 뒤 구현한다.**

### 구현 진입 전 은수님 승인이 필요한 것

| # | 확인 요청 |
|---|---|
| 1 | **작업 폴더 신규 생성**이 맞는지 (`20260901_1009_0x59-4.5-PMIC-상한`) |
| 2 | **앱 Default 상수(160·200)를 그대로 두는 것**이 맞는지 — 펌웨어 공장값은 112·172 다 |
| 3 | **하한 > 상한 조합을 앱이 목록에서 제외**하는 강도가 맞는지 (경고만 하고 허용하는 선택지도 있다) |

| 5 | 브랜치를 `develop_ota` 에서 이어가는 것이 맞는지 |

### 별도 보고 (앱 작업과 무관, 펌웨어 쪽)

**펌웨어가 «하한 > 상한» 을 막지 않는다.** `isd_interface.c:213` 주석은 *"하한의 허용 상한 (이 값 - 1)"* 이라고 적었는데 `tdc_is_valid_min_tx_power_level()`(`:198`)에 그 검사가 없다. 규격 문서의 인덱스 3·4 범위도 `72~213` 고정이다. **앱이 막아도 다른 리모콘·시험 도구는 넣을 수 있다.**
