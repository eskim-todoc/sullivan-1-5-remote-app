# 분석 검증

**TL;DR**: 요구사항 8건이 **전부 구현 지점을 얻었다.** 근거는 앱·펌웨어 양쪽에서 `파일:라인` 으로 확인했고, 인용 오류 1건을 정정했다. **요구사항_4 의 근거가 «추정» 에서 «확인됨» 으로 올라간 것**이 이 단계의 성과다 — 펌웨어가 하한 검사를 안 한다는 것을 코드로 봤다.

## 2. 논리적 정합성

### 2.1 요구사항 → 구현 지점 대응 (누락 검사)

| 요구사항 | 구현 지점 | 분석 근거 |
|---|---|---|
| 1 버전 게이팅 | `isLinkParamSupported` `case 16` + `isMaxTxPowerSupported()` | §1.1 |
| 2 개별 읽기 | 전체 읽기 4곳 뒤에 인덱스 16 읽기 추가. 파서는 그대로 | §1.2 |
| 3 하한선 계산 | 다이얼로그 진입 시 인덱스 3·4 값으로 목록 시작점 결정 | §1.3 |
| 4 하한 > 상한 차단 | 하한 다이얼로그 2곳에 상한 검사 | §2.1 |
| 4b Default 상수 보고 | 코드 변경 없음. 보고만 | §5 |
| 5 거부 사유 구분 | 에러 문맥 추적 + `case 2` 분기 | §1.5 · §2.2 |
| 6 «지금 파워는 그대로» 안내 | 낮추는 방향일 때 안내 | §4 위험 4 |
| 7 화면 표시 | Etc 2행 `Space` → 버튼, 상태 표시 추가 | §1.4 |

**누락 없음.** 8건 모두 지점이 있다.

### 2.2 위험 완화가 요구사항과 충돌하지 않는가

**위험 2 의 완화(«모름이면 검사를 건너뛴다»)가 요구사항_4 를 약화시키는가?** — 형식적으로는 그렇다. 그러나 그 상태는 **4.5 기기인데 인덱스 16 을 못 읽은 경우**뿐이고, 그때 앱이 하한 쓰기를 막으면 **4.3·4.4 에서 되던 조작이 4.5 에서 안 되는** 퇴행이 된다. 펌웨어가 어차피 하한을 다 받으므로 **막지 않는 쪽이 안전하다.** 판단 유지.

### 2.3 «앱이 마지막 방어선» 이라는 표현이 과한가

과하지 않다. 근거 셋이 같은 방향이다.

- 펌웨어 하한 쓰기에 상한 검사가 **없다** (`isd_interface.c:198`)
- 규격 문서의 인덱스 3·4 범위도 `72~213` 으로만 적혀 있다 (`0x59 프로토콜 규격.md:109~110`)
- 앱 하한 다이얼로그의 상한도 213 고정 (`PacketInfo.java:412`)

**세 층 어디에도 «상한보다 큰 하한» 을 막는 것이 없다.**

### 3.1 확신도 승급

> **요구사항_4 는 요구사항 단계에서 «분석에서 확인한다» 로 열어 둔 것이었다.**
> 이제 **확인됨** 이다 — `tdc_is_valid_min_tx_power_level()` 이 상한을 보지 않는 것을 코드로 봤다.
> 승급의 결과로 요구사항_4 의 강도가 «경고» 가 아니라 **«목록에서 제외»** 로 정해졌다(§5).

## 4. 남은 불확실

| # | 무엇 | 어떻게 다룰까 |
|---|---|---|
| 1 | 하한 > 상한 조합이 실제 링크 동작에서 어떻게 되는가 | **쓰기는 통과한다**까지가 확인된 것이다. 사용 시점에 클램프되는지는 안 봤다. 앱은 어차피 막으므로 **구현에 영향 없다.** 펌웨어 보고 항목으로만 남긴다 |
| 2 | 상한 쓰기 성공 응답이 값을 되돌려 주는가 | 다른 인덱스와 같다면 되돌려 준다. **쓰기 뒤 개별 읽기를 한 번 더 하는 것**으로 어느 쪽이든 안전하게 만든다 |
| 3 | 4.5 실기 | 4.4 도 실기 확인 대기다. 같이 대기 항목으로 쌓는다 |
