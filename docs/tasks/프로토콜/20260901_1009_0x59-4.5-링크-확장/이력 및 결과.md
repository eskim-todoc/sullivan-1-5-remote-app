## 결정과 근거

### 폴더를 새로 만든 이유

`docs/tasks/프로토콜/작업 목록.md` 에 4.4 작업 폴더 하나가 있고 «구현 완료 · 실기 확인 대기» 상태다. **다루는 인덱스(7·8)와 기능(재시도 코인)이 완전히 다르다.** 프로토콜 버전이 올라갈 때마다 폴더를 새로 만드는 것이 그 목록의 관례다.

### 요구사항_4 를 규격에 없는데도 넣은 이유

규격의 «앱이 해야 할 일» 은 넷인데 요구사항은 일곱이다. 차이 중 하나가 요구사항_4(하한이 상한을 넘는 조합 차단)다.

펌웨어는 **인덱스 16 을 쓸 때만** 하한과의 대소를 검사한다. 반대 방향 — 이미 정해진 상한보다 **큰 하한을 쓰는 것** — 은 규격에 언급이 없고, 앱의 하한 다이얼로그는 상한이 213 으로 고정돼 있어(`PacketInfo.MIN_TX_PWR_SELECT_MAX`) **상한을 201 로 낮춰 둔 상태에서 하한 210 을 고를 수 있다.** 분석 단계에서 그 조합이 실제로 만들어지는지, 만들어지면 펌웨어가 어떻게 받는지 확인한다.

## 결과

**구현 완료 · 실기 확인 대기.** 빌드(`assembleDebug`) 통과.

### 한 일

프로토콜 4.5 의 Tx 파워(PMIC) 상한(`0x20` 인덱스 16)을 앱에 반영했다. 5개 파일이 바뀌었고,
**4.3·4.4 기기에서 동작이 바뀌는 경로는 하나도 없다**(전수 확인은 `구현-검증.md` §3).

핵심은 **읽기 경로**다. 이 인덱스는 응답 20바이트 상한 때문에 전체 읽기에 실리지 않아,
**판별이 끝나 «4.5» 가 확정되는 자리에서 개별로 한 번 더 읽는다**(은수님 지시).

### 남은 것

- **펌웨어 보고 2건** — 하한 > 상한을 막지 않는 것 · 앱 Default 상수가 낡은 것 (`구현-검증.md` §6)
