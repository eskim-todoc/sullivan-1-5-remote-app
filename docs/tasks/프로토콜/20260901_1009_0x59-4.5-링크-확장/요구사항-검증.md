# 요구사항 검증

**TL;DR**: 요구사항 8건 중 **7건은 규격 문장에 직접 대응**하고, 1건(요구사항_4b)은 착수 중 발견한 앱 결함이다. 근거는 전부 `파일:라인` 으로 확인했고, **추측으로 적은 문장은 정정 후 남아 있지 않다.** 다만 **미검증 항목 3건**을 분석 단계로 넘긴다.

## 2. 논리적 정합성

### 2.1 규격의 «앱이 해야 할 일» 과 요구사항의 대응

규격(`0x59 버전 이력.md` §4.5 CAUTION)이 넷을 지정했다. **누락 없이 대응한다.**

| 규격이 시킨 것 | 대응 |
|---|---|
| ① 인덱스 16 은 개별 읽기로 가져간다 | 요구사항_2 |
| ② 쓰기 전 인덱스 3·4 를 읽어 큰 값 + 1 을 하한선으로 보여 준다 | 요구사항_3 |
| ③ `en__OutOfDataRange` 와 `en__unusableMapData` 를 구분해 표시 | 요구사항_5 |
| ④ 상한을 낮춘 직후 인덱스 1 이 그대로일 수 있음을 안내 | 요구사항_6 |

규격에 없는데 넣은 것은 셋이고 각각 이유가 있다.

| 추가 | 왜 필요한가 |
|---|---|
| 요구사항_1 (버전 게이팅) | 4.3·4.4 기기에 인덱스 16 을 보내면 «없는 인덱스» 응답이 온다. 기존 4.4 작업이 같은 방식으로 게이팅했으므로 관례이기도 하다 |
| 요구사항_4 (하한이 상한을 넘는 조합) | 펌웨어는 **인덱스 16 을 쓸 때만** 대소를 본다. 반대 방향은 규격에 없고, 앱 하한 다이얼로그의 상한이 213 고정이라 **넘는 조합을 고를 수 있다** |
| 요구사항_4b (Default 상수 낡음) | 착수 중 발견. 이 작업이 만드는 선택 범위를 직접 좁힌다 |
| 요구사항_7 (화면 표시) | 규격 밖이지만 기존 PMIC 3형제와 형태를 맞춰야 한다 |

### 2.2 요구사항끼리 충돌하는가

**충돌 없음.** 다만 **요구사항_3 과 요구사항_4b 가 같은 지점을 다르게 건드린다** — 3 은 «읽은 값으로 하한선을 계산하라», 4b 는 «Default 가 쓰는 값이 틀렸다». 3 을 제대로 구현하면 4b 를 고치지 않아도 **동작은 맞는다**(읽은 값이 200 이면 하한선 201 이 맞다). 4b 는 «범위가 왜 좁은가» 의 원인이지 3 의 전제가 아니다. **독립이다.**

### 2.3 요구사항_1 의 게이팅이 요구사항_2 를 무력화하지 않는가

전체 읽기는 모든 버전에서 돌고, 인덱스 16 개별 읽기만 4.5 이상에서 추가된다. **4.5 미만에서는 상한 값이 «모름» 상태로 남고 UI 가 숨겨지므로 모순이 없다.**

### 3.1 착수 중 정정한 것

> **처음에 «현재 기본값(160·200) 기준이면 201~214» 라고 썼다. 틀렸다.**
>
> 앱의 Default 버튼 상수를 펌웨어 기본값으로 착각한 것이다. 규격은 «173~214» 라고 적고 있었고,
> 그 차이를 추적해 펌웨어 실제 기본값(112·172)을 찾았다. **규격의 숫자와 내 계산이 안 맞으면
> 내 전제를 먼저 의심한다** — 이번에는 그 덕에 요구사항_4b(앱 상수 낡음)가 나왔다.

## 4. 분석 단계로 넘기는 미검증 항목

| # | 무엇 | 왜 지금 못 정하나 |
|---|---|---|
| 1 | **하한(3·4)을 상한보다 크게 쓰면 펌웨어가 어떻게 받나** | 규격에 없다. `tdc_file_link_param.c` 의 갱신 함수를 읽어야 한다. 요구사항_4 의 강도가 여기서 정해진다 |
| 2 | **에러 응답에 «어느 인덱스가 거부됐는지» 가 실려 오나** | 에러 패킷이 `[1]` 실패 커맨드 · `[2]` 에러 타입만 담는 것으로 보인다(`MainActivity.java:3843~3844`). 그러면 «상한 쓰기가 거부됐다» 를 **앱이 문맥으로 추론**해야 한다 |
