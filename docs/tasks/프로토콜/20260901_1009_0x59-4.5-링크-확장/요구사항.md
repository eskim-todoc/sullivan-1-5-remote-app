# 요구사항

**TL;DR**: 펌웨어가 **링크 제어가 올릴 수 있는 Tx 파워의 상한**을 리모콘으로 정할 수 있게 열었다(`0x20` 인덱스 **16**). 앱은 이 값을 **개별 읽기로만** 가져와야 하고, 쓸 수 있는 하한선이 **인덱스 3·4 에 따라 움직인다**. 그리고 **낮춰도 현재 파워가 즉시 내려가지 않는다**는 점을 사용자에게 알려야 오해가 없다.

## 1. 배경

은수님 지시 (2026-09-01): *"펌웨어에서 프로토콜 버전 업 됐어. 4.5로. 이거 맞춰서 작업좀 하자. PMIC 레벨 상한 조정 기능이야."*

앱 UI 는 Tx 파워 레벨을 **«PMIC»** 로 부른다 — `PMIC 하한 선택`(인덱스 3) · `매핑 PMIC 하한 선택`(인덱스 4) · `고정 PMIC 선택`(인덱스 6). 펌웨어 규격은 같은 것을 «Tx 파워» 로 부른다. **이 문서는 UI 어휘를 따라 «PMIC 상한» 으로 쓴다.**

동기는 규격이 밝히고 있다 — 링크 초기화의 램프업이 **75 에서 상한까지 올리고 끝나므로**, 상한을 낮추면 초기 전압이 그만큼 낮아진다. 은수님이 지목하신 «초기값이 높아서 생기는 이슈» 의 지점이다.

## 2. 4.5 가 바꾼 것

근거: 펌웨어 repo `docs/참고/리모콘 프로토콜/0x59 프로토콜 규격.md:122` · `0x59 버전 이력.md:119~135`

| 구분 | 내용 |
|---|---|
| 추가 | `0x20` 인덱스 **16** — PMIC 상한. **R/W**. 25mV 단위. 기본 **214**. `LINKPARM.TXT` 영속 |
| 범위 | **(인덱스 3·4 중 큰 값) + 1 ~ 214.** 펌웨어 공장 출하 기본값(인덱스 3 = **112**, 인덱스 4 = **172**) 기준이면 **173~214** 다 — 규격이 든 예와 같다 |
| **전체 읽기 제외** | 응답이 헤더 5 + 값 15 = 20 바이트로 `BLE_DataPacketSize` 에 꽉 차서, 전체 읽기는 **앞 15개로 고정**됐다. 인덱스 16 은 **개별 읽기로만** 받는다 |
| 쓰기 실패 분화 | 범위 밖이면 `en__OutOfDataRange`(BLE 에러 타입 **2**), 파일 기록 실패 등은 종전대로 `en__unusableMapData`. **기존 인덱스의 응답은 안 바뀌었다** |
| 유지 | 인덱스 1~15 의 뜻·순서·전체 읽기 응답 **모두 그대로**. 포맷 불변이라 minor 만 올랐다 |
| 동반 동작 | 낮춰도 **현재 파워를 끌어내리지 않는다.** 상승만 막히고 하강은 `High` 판정에 맡긴다(300ms 마다 1스텝) |
| 동반 동작 | **리셋 후 첫 내부기 연결까지는 파일 값 대신 214** 를 쓴다(`TDC_LINK_MAX_POWER_SAFE_BOOT`). 리셋 = 전원 투입·슬립 웨이크·매핑 앱 해제·OTA 슬롯 선택 |
| 유지 | **강제 고정(인덱스 6)의 상한은 214 그대로.** 정책 상한에 묶이지 않는다 |
| 파일 | `LINKPARM.TXT` 의 예약 자리를 썼다. 크기 40 불변 → **4.3·4.4 기기 리셋 없음**, 다운그레이드 안전 |

> [!NOTE]
> 규격이 **«앱이 해야 할 일» 네 가지**를 직접 적어 두었다(`0x59 버전 이력.md` §4.5 CAUTION).
> 아래 요구사항 2·3·5·6 이 그 넷에 각각 대응한다.

## 3. 요구사항

### 요구사항_1 — 4.3·4.4·4.5 를 함께 다룬다

한 앱이 세 버전의 사운드처리기를 모두 상대한다. **4.5 미만이면 PMIC 상한 기능을 통째로 숨긴다.** 판정은 기존 `isProtocolAtLeast(major, minor)` 를 재사용하고, 새 minor 상수를 더한다.

구버전에서 인덱스 16 을 읽거나 쓰면 «없는 인덱스» 응답이 오므로, **보내지 않는 것**이 맞다.

### 요구사항_2 — 개별 읽기로 가져온다

전체 읽기(인덱스 0)에 인덱스 16 이 실리지 않는다. **전체 읽기 뒤에 인덱스 16 개별 읽기를 한 번 더** 보내야 값이 채워진다.

전체 읽기가 일어나는 모든 경로(연결 직후·프로그램 변경·설정 변경 후 갱신)에서 같이 따라가야 하며, **4.5 미만에는 보내지 않는다**(요구사항_1).

### 요구사항_3 — 쓸 수 있는 하한선을 계산해 보여 준다

선택 목록의 최솟값이 **고정이 아니다.** `max(인덱스 3, 인덱스 4) + 1` 이고, 두 하한은 사용자가 바꿀 수 있다.

- 목록을 열 때 **그 시점의 3·4 값으로 하한선을 다시 계산**한다
- 하한선 미만은 **목록에 넣지 않는다** — 넣으면 거부될 값을 고르게 하는 것이다
- 하한선이 어디서 왔는지 **다이얼로그에 적는다** (어느 하한이 상한선을 밀어 올렸는지)

### 요구사항_4 — 상한이 하한 변경에 밀릴 수 있음을 막는다

인덱스 3·4 를 **상한 이상으로 올리면** 그 조합은 펌웨어에서 성립하지 않는다. 앱이 하한을 쓸 때도 **상한을 넘지 않는지 확인**하고, 넘으면 무엇을 먼저 바꿔야 하는지 알린다.

> 이 요구사항은 규격의 «앱이 해야 할 일» 에는 없다. **하한 쪽 다이얼로그의 상한이 213 으로 고정**되어 있어(`PacketInfo.MIN_TX_PWR_SELECT_MAX`) 사용자가 상한보다 큰 하한을 고를 수 있기 때문에 필요하다. 분석 단계에서 실제로 그런 조합이 만들어지는지 확인한다.

### 요구사항_4b — 앱의 Default 값이 펌웨어 기본값과 어긋난 것을 보고한다

착수 중에 드러났다. **앱의 «Default» 버튼이 쓰는 값이 펌웨어의 공장 출하 기본값과 다르다.**

| 인덱스 | 앱 상수 | 펌웨어 기본값 | 근거 |
|---|---|---|---|
| 3 상시 하한 | `MIN_TX_PWR_DEFAULT` = **160** (4.000V) | **112** (2.8V) | `driver_REN_ISL9122.h:46` — 2026-08-12 «공장 출하 기본값으로 확정» |
| 4 매핑 하한 | `MAPPING_TX_PWR_DEFAULT` = **200** (5.000V) | **172** (4.3V) | `isd_interface.c:82` — 2026-08-12 «공장 출하 기본값으로 확정» |

앱 값 둘 다 **2026-08-05~06 시점의 값**이고, 08-12 에 확정된 값으로 갱신되지 않았다.

이 작업과 맞닿는 이유 — Default 를 누르면 매핑 하한이 **200** 이 되고, 그러면 상한의 하한선이 **173 이 아니라 201** 로 뛴다. 즉 **이 작업이 만드는 화면의 선택 범위가 낡은 상수 때문에 좁아진다.**

**고칠지 말지는 은수님 판단이다.** 값 변경은 링크 동작에 직접 영향을 주고, 이 작업의 지시(«상한 조정 기능»)에는 없다. 기본은 **보고만 하고 손대지 않는 것**으로 둔다.

### 요구사항_5 — 거부 사유를 구분해 표시한다

쓰기 실패가 두 갈래다.

| 사유 | 펌웨어 응답 | 앱 표시 |
|---|---|---|
| 값이 범위 밖 | `en__OutOfDataRange` (BLE 에러 타입 **2**) | «범위 밖» — 지금 쓸 수 있는 범위를 함께 알린다 |
| 파일 기록 실패 등 | `en__unusableMapData` | «저장 실패» |

현재 앱은 에러 타입 1·2·8 을 **한 덩어리로 «유효하지 않은 명령어»** 라고만 띄운다(`MainActivity.java:3859~3862`). 그 문구로는 사용자가 무엇을 고쳐야 하는지 알 수 없다.

### 요구사항_6 — «낮춰도 지금 파워는 그대로» 를 안내한다

상한을 낮춘 직후 인덱스 1(현재 파워)이 그대로일 수 있다. **정상이다.** 사용자가 «설정이 안 먹었다» 로 오해하지 않도록 낮추는 방향일 때 안내한다.

### 요구사항_7 — 화면 표시

- 상한 값을 **전압과 레벨 둘 다** 보여 준다 (기존 PMIC 다이얼로그와 같은 `%.3f V (레벨 %d)` 형식)
- 기본값(214)으로 되돌리는 **Default** 버튼을 둔다 — 기존 PMIC 다이얼로그의 관례
- 버튼 위치와 이름은 기존 PMIC 3형제(`PMIC`·`BT PMIC`·`Fixed PMIC`) 옆에 둔다

## 4. 제약

| 제약 | 내용 |
|---|---|
| 규격 준수 | 인덱스·범위·응답 코드는 **펌웨어 문서가 유일한 근거**다. 임의로 넓히거나 좁히지 않는다 |
| 하위 호환 | 4.3·4.4 기기에서 **기존 동작이 하나도 바뀌면 안 된다** |
| 전체 읽기 | `RC_LINK_IDX_MAX` 를 16 으로 올릴 때 **전체 읽기 파서가 15개만 받는다는 전제**를 깨면 안 된다 |
| 강제 고정 | 인덱스 6 의 상한 214 는 **건드리지 않는다.** 정책 상한과 무관하다 |
| 미검증 | 실기 확인 전까지 **«확인됨» 으로 적지 않는다.** 4.4 작업도 실기 확인 대기 상태다 |
