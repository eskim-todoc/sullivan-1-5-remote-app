# 분석

**TL;DR**: 인덱스 추가 자체는 기존 골격에 그대로 얹힌다. **진짜 문제는 셋이다** — ① 전체 읽기에 안 실리므로 **읽기 경로를 하나 더 만들어야** 하고, ② 에러 응답에 **인덱스가 없어** «무엇이 거부됐는지» 를 앱이 문맥으로 알아야 하며, ③ **펌웨어가 «하한 > 상한» 조합을 막지 않는다** — 앱이 마지막 방어선이다.

## 1. 앱의 현재 골격

### 1.1 인덱스와 버전 게이팅

| 무엇 | 어디 |
|---|---|
| 인덱스 상수 | `PacketInfo.java:178~192`, 마지막이 `RC_LINK_IDX_STIM_STRATEGY = 15` |
| «이 앱이 아는 마지막 인덱스» | `PacketInfo.java:194` `RC_LINK_IDX_MAX = 15` |
| minor 상수 | `PacketInfo.java:233~246` — `NOP=1` · `NOP_TABLE=2` · `STRATEGY=3` · `COIN_COUNT=4` |
| 인덱스별 게이팅 | `MainActivity.java:952` `isLinkParamSupported(int index)` — 인덱스마다 «어느 minor 에서 생겼나» 로 가른다 |
| 기능 단위 게이팅 | `MainActivity.java:1175` `isCoinCountSupported()` — 인덱스 게이트와 **따로** 둔 선례 |

**4.5 는 이 구조에 그대로 들어간다.** `MINOR_MAX_TX_POWER = 5` 를 더하고, `isLinkParamSupported` 의 `switch` 에 `case 16` 을 추가하면 된다.

> [!WARNING]
> **`RC_LINK_IDX_MAX` 를 16 으로 올릴 때 주의할 곳이 둘 있다.**
>
> ① 전체 읽기 파서 `MainActivity.java:2562` 는 `Math.min(valueLen, RC_LINK_IDX_MAX)` 로 자른다.
> 4.5 기기의 전체 읽기 응답은 값이 **15개**이므로 `min(15, 16) = 15` — **안전하다.**
>
> ② 같은 `switch` 의 `default` 가 `return (index <= RC_LINK_IDX_MAX)` 다(`MainActivity.java:971~972`).
> **16 을 `default` 에 맡기면 4.3·4.4 기기에서도 «지원됨» 이 되어 버린다.** 반드시 `case` 를 따로 둔다.

### 1.2 읽기 경로

전체 읽기(`RC_IDX_ALL = 0`)를 보내는 곳이 네 군데다 — `MainActivity.java:1042` · `:1113` · `:1448` · `:2327`. 응답은 `handleRcLinkResponse()`(`:2554`)가 받아 `applyLinkParam()`(`:2597`)으로 인덱스별 뷰모델에 넣는다.

**개별 읽기 경로도 이미 있다.** 같은 함수의 `index != RC_IDX_ALL` 분기(`:2578~2593`)가 값 하나를 받아 같은 `applyLinkParam()` 으로 흘린다. 즉 **인덱스 16 은 파서를 고칠 필요가 없고, «보내는» 쪽만 추가하면 된다.**

### 1.3 PMIC 3형제 다이얼로그

| 기능 | 인덱스 | 다이얼로그 | 제목 |
|---|---|---|---|
| 상시 하한 | 3 | `RemoteControlFragment.java:1416~1476` | `PMIC 하한 선택` |
| 매핑 하한 | 4 | `:1531~1578` | `매핑 PMIC 하한 선택` |
| 강제 고정 | 6 | `:1860~1910` | `고정 PMIC 선택` |

셋이 **같은 형태**다 — `min~max` 를 목록으로 펼치고, `%.3f V (레벨 %d)` 로 찍고, 현재 값을 체크해 두고, `Default` 버튼을 단다. **상한 다이얼로그는 이 형태를 그대로 따르면 된다.** 다른 점은 하나 — **최솟값이 고정이 아니다.**

### 1.4 화면 배치

| 자리 | 내용 | 근거 |
|---|---|---|
| 상태 표시 1행 | `Cur` / `PMIC` / `Map` / `Fix` | `fragment_remote_control.xml:51~110` |
| Etc 1행 | `Map` / `Gating` / `Normal PMIC` / `BT PMIC` | `:1340~1420` |
| Etc 2행 | `BT Period` / `Link Step` / `Fixed PMIC` | `:1428~` |

**Etc 2행에 «비워 둔 칸» 이 정확히 하나 있다.** XML 주석이 명시한다 —
*"버튼이 3개라 오른쪽 한 칸은 Space 로 비워 둔다. 윗줄과 같은 4열 격자를 유지해야 열이 맞기 때문이다"*
(`fragment_remote_control.xml:1430~1431`). **그 `Space` 를 버튼으로 바꾸면 격자가 그대로 채워진다.**
버튼 이름은 3형제와 결이 맞게 `Max PMIC` 가 자연스럽다.

### 1.5 에러 처리

```
MainActivity.java:3843  byte errorType = byteExtractor(responsePacket[2]);
MainActivity.java:3844  byte failedCmd = byteExtractor(responsePacket[1]);
MainActivity.java:3859  case 1: case 2: case 8:  →  "사운드처리기가 유효하지 않은 명령어를 전송했습니다."
```

에러 패킷은 6바이트(`PacketInfo.java:70`)이고 담는 것은 **실패 커맨드와 에러 타입뿐**이다. **어느 옵션·어느 인덱스가 거부됐는지는 실려 오지 않는다.**

## 2. 미검증 3건의 해소

### 2.1 «하한을 상한보다 크게 쓰면?» → **펌웨어가 받는다. 막지 않는다**

```c
// isd_interface.c:198
bool tdc_is_valid_min_tx_power_level(int level)
{
    return ((TDC_MIN_TX_POWER_LEVEL_LOWER <= level) && (level <= TDC_MIN_TX_POWER_LEVEL_UPPER));
}
```

**상한을 보지 않는다.** 그리고 인덱스 3·4 의 갱신 함수(`tdc_file_link_param.c:369` · `:443`)는 이 검사 하나만 쓴다. 즉 **상한 180 인 상태에서 하한 210 을 쓰면 성공한다.**

반대 방향만 검사한다.

```c
// isd_interface.c:260
bool tdc_is_valid_max_tx_power_level(int level)
{
    return ((tdc_get_max_tx_power_level_floor() < level) && (level <= TDC_MAX_TX_POWER_LEVEL_UPPER));
}
```

> [!CAUTION]
> **펌웨어 주석과 구현이 어긋난다.** `isd_interface.c:213` 이 상한이 정하는 것으로
> *"하한의 허용 상한 (이 값 - 1)"* 을 들고 있는데, **하한 쓰기 경로에 그 검사가 없다.**
> 규격 문서에도 인덱스 3·4 의 범위는 `72~213` 으로만 적혀 있다(`0x59 프로토콜 규격.md:109~110`).
>
> **이것은 앱이 고칠 수 없는 펌웨어 쪽 사안이다.** 은수님께 보고한다.
> 앱은 그동안 **자기 쪽에서 막는다**(요구사항_4).

### 2.2 «에러 응답에 인덱스가 실리나» → **안 실린다**

§1.5 대로 실패 커맨드(`0x59`)와 에러 타입만 온다. 따라서 «상한 쓰기가 범위 밖으로 거부됐다» 를 알려면 **앱이 «마지막으로 무엇을 썼는지» 를 기억**하고 있어야 한다.

선례가 있다 — `MainActivity.java:3850` 이 «세대 판별 중» 이라는 문맥을 `isLinkInfoReadIdle()` 로 판단해 같은 에러를 다르게 처리한다. **같은 방식으로 «상한 쓰기 대기 중» 문맥을 두면 된다.**

### 2.3 «버튼을 어디에» → **Etc 2행**

§1.4 대로 자리가 있다. 태블릿 2단 레이아웃은 `RemoteControlFragment.applyTabletTwoColumnLayout()` 이 런타임에 재배선하므로, XML 에 버튼을 추가하면 자동으로 따라간다(Etc 는 왼쪽 열 하단).

## 3. 영향 범위

| 파일 | 무엇 |
|---|---|
| `params/PacketInfo.java` | 인덱스 16 상수 · `RC_LINK_IDX_MAX` 16 · `MINOR_MAX_TX_POWER = 5` · 상한 선택 범위·기본값 상수 |
| `activity/MainActivity.java` | `isLinkParamSupported` 에 `case 16` · `isMaxTxPowerSupported()` · 전체 읽기 뒤 개별 읽기 · `applyLinkParam` 에 `case 16` · 상한 쓰기 함수 · 에러 문맥 판단 · 연결 해제 시 값 초기화 |
| `view_model/StatusViewModel.java` | `MaxTxPowerLevel` LiveData 한 벌 (기존 `MinTxPowerLevel` 과 같은 형태) |
| `fragment/RemoteControlFragment.java` | `Max PMIC` 다이얼로그 · 하한 다이얼로그에 상한 검사 · 상태 텍스트 갱신 · LiveData 관찰 |
| `res/layout/fragment_remote_control.xml` | Etc 2행에 버튼 · 상태 표시에 값 |

**기존 인덱스의 동작을 바꾸는 곳은 없다.** 하한 다이얼로그에 «상한을 넘지 않는지» 검사가 하나 더해질 뿐이다.

## 4. 위험

| # | 위험 | 완화 |
|---|---|---|
| 1 | `RC_LINK_IDX_MAX` 를 16 으로 올리면 `default` 게이트가 4.3·4.4 에서도 16 을 «지원» 으로 판정 | `case 16` 을 명시적으로 둔다 (§1.1) |
| 2 | 상한을 못 읽은 상태(4.5 이지만 개별 읽기 실패)에서 하한 검사가 오작동 | «모름» 값(`LINK_VALUE_UNKNOWN`)이면 **검사를 건너뛴다.** 막는 쪽이 아니라 통과시키는 쪽으로 둔다 — 펌웨어가 어차피 하한은 다 받는다 |
| 3 | 에러 문맥 추적이 다른 쓰기와 섞임 | 문맥에 **타임아웃**을 둔다. 선례(`isEnabledInvalidPacketToast` 의 3.5초 억제)와 같은 방식 |
| 4 | 상한을 낮춘 뒤 사용자가 «안 먹었다» 로 오해 | 낮추는 방향일 때만 안내 (요구사항_6) |
| 5 | 실기 확인 불가 상태로 병합 | 4.4 작업과 같이 «실기 확인 대기» 로 둔다. `docs/상시 점검 대장.md` 에 항목을 쌓는다 |

## 5. 열어 두는 결정

| 결정 | 선택지 | 기울기 |
|---|---|---|
| 앱 Default 상수 갱신(요구사항_4b) | ⓐ 그대로 두고 보고만 ⓑ 펌웨어 값(112·172)으로 맞춤 | **ⓐ** — 지시 범위 밖이고 링크 동작에 직접 영향 |
| 하한 > 상한 차단 강도 | ⓐ 목록에서 제외 ⓑ 경고만 하고 허용 | **ⓐ** — 거부될 값을 고르게 하지 않는다는 요구사항_3 과 일관 |
| 버튼 이름 | `Max PMIC` / `PMIC 상한` | **`Max PMIC`** — 3형제가 영문 축약(`Normal`·`BT`·`Fixed`) |
