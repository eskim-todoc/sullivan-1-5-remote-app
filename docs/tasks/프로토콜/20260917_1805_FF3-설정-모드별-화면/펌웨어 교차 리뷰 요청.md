# FF3 앱/펌웨어 교차 리뷰 요청

## 1. 검토 요청의 핵심

2026-10-01 SM-X205N 태블릿과 `TD_L_PEK_FFFF`에서 FF3를 읽고 진단했다. **FF3 설정과 진단 응답은 정상적으로 받았으며, 실제 가산 쓰기 기록도 확인했다. 다만 연속 전체 조회에서 두 번 무응답이 발생했다.** 앱의 FF3 요청 간격을1ms에서50ms로 늘린 뒤에는 전체 조회3회가 성공했다.

펌웨어 측에서 먼저 확인할 사항은 “응답을 앱에 전달한 직후 다음 요청이 들어오면 수신/응답이 유실될 수 있는가”다.50ms는 앱의 경험적 완화이며 원인 확정이나 명세상 최소 지연으로 합의한 값은 아니다. 실제 실패 패킷, 현재 설정 보존 결과와 진단 해석 질문을 아래에 모았다. 이 문서만 전달해도 검토 조건과 질문을 알 수 있으며, 원시 로그는 앱 저장소의 링크에서 추가 확인할 수 있다.

사용자가 비착용 테스트 내부기 연결 상태임을 확인한 뒤 OFF/BEGIN/ABORT, G11→12 저장, 별도 모드3 활성화, 편집 중 재접속/계속, G11 복원 저장과 모드3 복원을 실증했다. 종료 재접속에서도 최초69개 설정과 모드3/status0x19가 일치했다. 제어 순서는 성공했지만 앞선 무응답 원인은 여전히 미확정이다. 장치 전원 재부팅과 외부 전압/자극 계측은 수행하지 않았다.

## 3. 확인된 문제: 연속 조회 중 응답 없음

### 3.1 재현한 두 구간

패킷 바이트는16진수이고 인덱스 설명은10진수다. 아래는 앱 logcat 기록이며 RF 캡처나 펌웨어 수신 로그가 아니다.

| 시각 KST | 방향 | 패킷 / 관찰 |
|---|---|---|
| 14:37:30.280 | 장치→앱 | `59 20 00 58 01 00`, index88 응답 정상 |
| 14:37:30.282 | 앱 송신 시도 | `59 20 00 59`, index89 읽기 |
| 14:37:33.292 | 앱 | 3초 시한까지 대응 응답/F0 없음, FF3 시간 초과 |
| 14:41:03.246 | 장치→앱 | `59 20 00 47 01 00`, index71 응답 정상 |
| 14:41:03.249 | 앱 송신 시도 | `59 20 00 48`, index72 읽기 |
| 14:41:06.260 | 앱 | 3초 시한까지 대응 응답/F0 없음, FF3 시간 초과 |

index89와72는 미사용 행의 Δ/하한이며 모두0이었다. 다른 전체 조회에서는 동일 인덱스의 정상 응답을 받았다. 따라서 “해당 인덱스가 미지원이다” 또는 “그 값이 범위를 벗어났다”는 설명만으로는 관찰을 설명하기 어렵다. 첫 실패 후 앱을 재실행하여 자동 BLE 재연결했을 때 전체 조회는 성공했고, 같은 연결에서 수동 재조회는 다시 실패했다.

송신 로그는 `writeCharacteristic` 호출 전에 출력된다. 당시 앱은 GATT 쓰기 완료 status를 기록하지 않았으므로 이 로그만으로 장치가 요청을 실제로 수신했다고 단정할 수 없다. 동기적인 패킷 전송 실패 로그는 없었다. 무선 유실, Android GATT 순서 문제, BLE 중계 응답 유실, CM3의 수신 처리 문제 모두 미확정이다.

### 3.2 앱에서 적용하고 확인한 완화

`MainActivity.sendPacket`에서 FF3 트랜잭션의 요청만50ms 뒤 전송한다. 일반 명령 간격, 패킷, 요청 순서, 응답 시한은 유지했다. GATT 쓰기 완료가 실패 status이면 로그로 남기도록 보강했다. 쓰기/모드 변경의 자동 재전송은 추가하지 않았다.

| 전체 조회 | schema 읽기 송신 → 마지막 index111 응답 | 결과 |
|---|---|---|
| 자동 조회 | 14:44:58.791 → 14:45:06.823 | 전체 성공 |
| 수동 재조회1 | 14:45:33.031 → 14:45:43.316 | 전체 성공 |
| 수동 재조회2 | 14:45:56.611 → 14:46:06.938 | 전체 성공 |

69개 설정은 최초값과 모두 같았고 mode3/status0x19/파일 확인0을 유지했다.3회 성공은 이번 조건의 근거이며 장기 안정성 보장은 아니다.

### 3.3 펌웨어 측 확인 요청

1. 장치가 indication을 보낸 뒤 확인(HVC)이 끝나기 전에 다음 앱 요청을 받는 경우, 입력 또는 응답을 버리는 경로가 있는가? BLE 중계와 CM3 양쪽에서 응답 완료/수신 준비 상태를 확인해 달라.
2. 요청을 하나씩 보내고 앱 응답 콜백을 받은 다음 송신하는 것으로 충분한가? 추가 대기가 필요하다면 근거와 대기 종료 조건이 무엇인가?50ms 같은 고정 간격이 계약이어야 하는지, 장치의 상태 처리로 해결할지 판단해 달라.
3. 같은 장치 빌드에서 index72/89 요청 수신, 옵션0x20 핸들러 진입, 응답 생성/중계 전송/indication 완료까지 각각 확인할 수 있는가? 앱 송신 시도와 실제 펌웨어 수신을 구분하는 추적이 필요하다.
4. 해당 장치의 실제 CM3/CFX/BLE 빌드가 전달 명세의 schema3/4.6과 같은 계약인지 확인해 달라. 버전4.6과schema3는 응답으로 확인했지만 빌드 식별자는 확보하지 못했다.

명세와 함께 볼 처리 위치는 `remoteControl_protocol.c:tdc_rc_proto_link`, `tdc_file_link_param.c:tdc_audio_ff_protocol`, 해당 BLE 중계의 요청/응답 전달 경로다. 특정 중계 파일이나 유실 원인을 확인하지 않은 상태에서 확정하지 않는다.

## 4. 계약 확인: 현재 G11 표의 보존

새 전달 명세의 시험 기본표는 G20, Δ4/4/4/4/4지만 실제 장치 파일은 G11, Δ4/3/2/1/1이다. 앱은 현재값 전체를 읽고 표시했으며 연결/업데이트에서 새 기본값을 쓰지 않았다. 읽기만 한 단계에서는 파일 generation2와CRC도 그대로였다. 후속 가역 쓰기 시험에서는 G만12로 바꿨다가11로 복원했다. 나머지68개 설정은 보존했고 종료 때 전체69개가 최초값과 같았다. 저장/모드 변경 후 파일 메타데이터는 generation8/CRC0xd4dc51f6으로 달라졌으며 확인0이었다. 최초 G11 표를 잘못된 앱 설정으로 보고 자동 교체하지 않았다.

펌웨어 측에서는 다음을 확인해 달라.

- 유효한 기존 파일이 컴파일 기본값보다 우선하며, 이 장치에서 G11 표가 유지되는 것이 의도한 동작인가?
- 새 표를 시험하려면 Δ합계20에 맞춰 G도20 이상으로 바꾸는 명시적 부분 편집이 맞는가? 현재 앱 검증은 Δ합계≤G와 상위Δ 비증가를 검사한다.
- 구간/필터/시간을 보존하고 바뀐 인덱스만 보내는 방식이 schema3 편집 계약에 맞는가?

## 5. 진단 해석 확인

### 5.1 실제 FF3 실행을 나타낸 기록

첫 두 번의 자연 입력 진단에서 FF 쓰기는330→344, event302→315, 스냅샷362615→378875였다.113의 result=2, 실제Δ=2, age=1ms, 장부=1, mode=3을 확인했다. 수정 앱에서도14:47:16~17과14:47:36~37 조회 사이에 FF 쓰기685→707로 증가했다.

수정 앱의 실제 응답 예:

```text
14:47:16.508 RX 59 20 00 71 0F A4 03 09 09 02 02 00 02 7B 01 00 05 E2 01 03
14:47:16.643 RX 59 20 00 72 0F 0C 76 25 00 02 AD 00 00 01 00 00 01 00 00 00
14:47:36.594 RX 59 20 00 71 0F 9F 00 07 07 02 02 00 02 90 01 00 05 E2 01 03
14:47:36.711 RX 59 20 00 72 0F 0C C3 26 00 02 C3 00 00 01 00 00 01 00 00 00
```

index113 첫 응답의 P=164/R=3/U=9/A=9/Δ=2/result2/event635/age1/session1506/장부1/mode3을 앱이 표시한다. 다음 응답은 P159/R0/U7/A7/Δ2/result2/event656이다. index114의 FF 쓰기0x2AD=685, 다음0x2C3=707로 해석했다.

이 결과는 “펌웨어가 FF3 가산 쓰기를 성공으로 보고했다”까지의 근거다. 외부 PMIC rail/전류/실제 자극을 계측하지 않았고 일정 음압 자극도 주지 않았다. 보호 성능이나 원래 설정의 적합성을 통과로 표시하지 않았다.

## 6. 실제 제어 결과와 남은 실증

앱 구현의 저장 순서는 OFF 쓰기/재조회0 → BEGIN → 변경 인덱스만 쓰기 → VALIDATE → SAVE_APPLY → 전체 설정/모드/status/파일 재조회 → CFX ACK 확인이다. 저장 후 OFF를 유지하고 메인에서 별도로mode3를 선택한다. 각 요청의 에코를 확인하고 F0/시간 초과 뒤 후속 쓰기를 중단한다.

CFX ACK가 아직 없으면100ms 간격 최대20회 status를 읽으며 각 요청 응답 시한은 별도로3초다. “전체 대기 시간이 반드시2초”라는 보장으로 표시하지 않는다. 펌웨어의 비동기 ACK 계약과 이 앱의 유한 대기가 맞는지도 확인해 달라.

| 시험 | 실제 결과 / 남은 확인 |
|---|---|
| OFF→BEGIN→ABORT | 성공. OFF/편집 시작 응답 후 ABORT(14:56:23.450 송신), 실행값69개 보존, 편집 종료, OFF 유지 |
| 잘못된 합계 차단 | 성공. Δ합계11에 G10 입력 시 앱 오류 표시. G10 쓰기/VALIDATE/SAVE_APPLY는 보내지 않음. 펌웨어에 잘못된 값을 직접 보내는 시험과 시간/미사용행 오류 실기는 미수행 |
| G11→12 저장 | 성공. index50만 변경, 에코→VALIDATE→SAVE_APPLY→전체 되읽기. 차이는 G 한 개, CFX ACK/파일 성공, OFF 유지 |
| 별도 활성화 | 성공. 14:58:46.969 mode3 송신, 재조회3. FF 쓰기1054→1062, 결과2/Δ2/장부1 |
| 편집 중 재접속 | 성공. OFF/BEGIN 후 앱 재실행, 남은 편집 표시. 자동 BEGIN 없이 사용자가 이전 편집 계속을 선택 |
| G12→11/모드3 복원 | 성공. 복원 저장 후 OFF, 별도로 모드3 선택. 최종 BLE 재접속 때 최초69개와 mode3/status0x19 일치 |
| 장치 전원 재부팅 | 미수행. BLE 재접속과 구분. 전원 후 파일 복원은 추가 시험 필요 |
| 계측 | 미수행. 통제 음압과 마이크/요청/I2C/PMIC rail/자극을 같은 시간축에서 확인 필요 |

G12 저장의 실제 요청/응답(16진수)은 다음과 같다. 로그의 `01`은 payload 길이이며 성공 코드가 아니다.

```text
14:57:41.951 TX 59 20 01 32 0C       # index50 G=12
14:57:42.060 RX 59 20 01 32 01 0C
14:57:42.129 TX 59 20 01 25 02       # VALIDATE
14:57:42.210 RX 59 20 01 25 01 02
14:57:42.261 TX 59 20 01 25 03       # SAVE_APPLY
14:57:42.888 RX 59 20 01 25 01 03
```

전체 되읽기 뒤 파일은 generation4/CRC0x02a79ae9/확인0, 모드는0이었다. 별도 활성화 뒤 generation5/CRC0x4b0ef1a5였다. G11 복원 저장은15:01:37.249에 index50=0B를 보내고 VALIDATE/SAVE_APPLY 응답을 받았으며 파일 generation7/확인0이었다. 마지막 모드3 복원과 재접속 뒤 generation8/CRC0xd4dc51f6/확인0을 읽었다. 이 제어 단계에서는 F0/FF3 시간 초과를 관찰하지 않았다. 로그 파일은 동일 PID의 앞선 기록을 포함하므로 해당 시각 이후를 대조한다.

펌웨어 측에서는 **모드 변경도 파일 세대를 증가시키고, 설정값을 원상 복원해도 generation/CRC가 최초값과 같아질 필요는 없다는 계약**이 이 빌드와 맞는지 확인해 달라. OFF 상태에서 BEGIN/ABORT와 재접속 편집 계속이 이번 관찰처럼 동작하는지도 교차 확인해 달라.

## 7. 검토 회신과 앱 측 후속

이 문서의 환경/파일 세대/원시 패킷은14:37~15:03 최초 제어 실증 기준이다. 이후 사용자 요청으로 FF3 용어와 목적별 화면을 개편했고 감지 증가 폭6→5→6dB의 저장/별도 켜기와 오류/취소를 추가 실증했다. 요청 인덱스/단위/저장 순서/50ms 간격 계약은 바꾸지 않았다. 최초69개와 모드3/G11/감지6을 다시 복원했으며, 후속 파일generation16/CRC0x66996e99/확인0이다. 최신 UI와 추가 시험 APK/로그는 [작업 기록](작업.md)의 사용성 개편 항목에서 확인한다. 최초 실증의 APK/파일generation8과 구분해서 검토해 달라.

펌웨어 측 회신에는 실제 빌드 식별자, 각 질문의 정상/수정 필요/미확인 판정, 근거 함수나 로그, 재시험 조건을 남겨 달라. 앱 측은 그 결과에 따라 고정 간격 완화를 유지하거나 전송 완료 경계를 수정하고, 같은 장치와 같은69개값에서 다시 검증한다. 펌웨어에서 정상이라고 확인한 진단은 사용 안내에 반영하고, 표시 위치/단위가 틀린 항목은 앱을 고친다.

## 8. 읽는 방식 MA2 고정처럼 보이는 문제 후속 (16:29~16:34)

사용자가 읽는 방식 버튼이 MA2로만 고정되어 비활성이라고 보고했다. 앱 조회 화면의 편집 잠금이 선택 버튼까지 가려 변경 진입을 찾기 어려운 문제였다. 선택 버튼에서 편집 시작 안내를 열고 BEGIN/전체 조회 완료 후 raw·MA2·AR 선택 창을 여는 방식으로 수정했다. 저장 프로토콜이나 index59의 의미는 바꾸지 않았다.

실제 TD_L_PEK_FFFF에서 MA2(1)→raw(0)→AR(2)→MA2(1)를 각각 저장했고, 전체69개 되읽기에서 선택값만 바뀌었다. [raw 저장](읽는방식-20261001/raw-저장.log)의 TX `59 20 01 3B 00`/RX `59 20 01 3B 01 00`, [AR 저장](읽는방식-20261001/AR-저장.log)의 TX `59 20 01 3B 02`/RX `59 20 01 3B 01 02` 이후 VALIDATE/SAVE_APPLY/되읽기가 성공했다. [MA2 복원](읽는방식-20261001/MA2-복원.log) 뒤 이번 시작69개와 불일치0, 모드OFF/status0x19, generation20/CRC0x2e87cd2b/확인0이다. 사용자 시험 시작 때 이미OFF였으므로 계속OFF로 남겼다. 필터별 실행 성능·CFX 감지 지연은 이번 저장 시험으로 입증하지 않는다. 최신 APK 식별자와 화면은 [작업 기록](작업.md)의 해당 항목을 따른다.
